# breadcrumb, notes for agents

How the tool behaves, for agents working on or with it. The source in `src/` is the authority, `breadcrumb --help` and `breadcrumb guide` list commands and conventions. `crumb` is the same binary under a shorter name.

## Storage

Notes are plain markdown files with YAML frontmatter, every write is a git commit, and `breadcrumb sync` pushes to whatever remote you set. Run `breadcrumb guide` for the agent conventions.

## Importing Claude Code memory

`breadcrumb import claude` pulls in Claude Code auto-memory, `--retire-index` swaps each MEMORY.md for a pointer to breadcrumb and keeps the old one as MEMORY.md.breadcrumb.bak. The vault lives at ~/breadcrumb unless `BREADCRUMB_HOME` says otherwise.

## Workflows

`breadcrumb workflow save .claude/workflows/*.js` keeps Claude Code workflow scripts in the vault, `breadcrumb workflow install` puts them back on another PC.

## Hooks

`breadcrumb hooks install` adds Claude Code hooks to ~/.claude/settings.json: SessionStart injects a short vault digest for the current project, SessionEnd imports new Claude Code auto-memory and starts a background `breadcrumb sync` when the vault has unsynced changes. `breadcrumb hooks uninstall` removes them again. Two more hooks inject one line each, and only when something matches: UserPromptSubmit names up to 3 notes relevant to the first prompt of a session, PreToolUse on Read, Edit, Write, MultiEdit and NotebookEdit names notes whose `paths` globs match the file (`breadcrumb add --path-glob 'src/engine/**'`), never the same note twice per session. A Stop hook asks once per session for a handoff note when the session changed the project's notes and wrote none. Skip them with `--no-recall`, `--no-file-notes`, `--no-handoff` or `--no-import`.

## Digest

The digest (`breadcrumb context`, the `context` tool and the SessionStart hook) fits in about 6000 chars, so nothing important is cut off at the end. Every pinned note gets one line, `id kind summary`, no slug because pins are rules and not named to the user, from its `summary` field (`breadcrumb add --summary ...`) or else its title's first sentence, decisions and preferences first and newest first, and agents `get` the body when they need it. Then the project's live handoffs, the unpinned preferences on one line, the backlog and recent notes. A handoff belongs to the session that wrote it, optionally to a `--track <word>`. A new one supersedes (a `supersedes` link) and unpins only the live handoff of its track, or with no track its own session's, never another session's unless `--supersedes <id or slug>` asks for it, and `add` prints what it superseded or which other handoffs stay live. Old handoffs with no session stamp are never superseded by themselves. The digest shows the newest live handoff in full and up to 3 others as one line each, `slug id who age: title`, those older than 7 days only when pinned. Superseded notes, by a `supersedes` link, a `superseded` tag or `decision_status: superseded`, never show in the digest.

## What the user said

A feedback or user note can keep the user's exact words: `--said "..."` on add and update (`said` in the MCP fields), with `said_on`, the date, defaulting to today, and `--unset said` drops both. Handoffs and feedback notes separate what the user said from what the writer concluded. Pin lines mark a feedback or user note with no `said` by `(inferred)` after the kind, but only for notes created on or after the cutoff in digest.rs, older ones mostly quote the user in their body in forms no check can tell from a paraphrase.

## Expiring notes

The CLI takes the MCP words too: `backlog` is `board`, `kinds` or a bare `kind` lists kinds, `question` is `ask`, `withdraw` is `unask`, `unlink` is `link --remove`, `map brief` is `brief`, `claim --release` is `release`, `delete --confirm` and `doctor --apply` are `--yes`, and `--tags`, `--fields`, `--refs`, `--paths`, `--steps`, `--lines` and `--pinned` work beside the singular flags. A bare sha of 7 to 40 hex characters given to `--ref` reads as `commit:<sha>`. `tree` places an item by its parent field, else its first `parent` link, else its first `part-of` link, and rewrites nothing. Board progress, the digest, the web page and `--json` agree with it, `update --field parent=<id>` sets the field.

Pins get retired by a person or lead, never automatically. `breadcrumb doctor` reports, as info so its error and warning counts stay comparable, pinned decisions whose body reads as finished, like a line of its own `2026-10-21 12:30: done.`, and pins not verified for `pin_review_days` (breadcrumb.toml, default 30, 0 turns it off). A pin ages from `pin_verified`, a date only `verify` sets, else from `created`, an append or update does not reset it. `verified` still moves on every write and only feeds the stale check. `breadcrumb pins [--project p | --all]` lists every pin with its age and why it is flagged, flagged first, with the commands to verify, unpin or archive it, and changes nothing. Every write sets `verified`, so a pin that was touched reads as fresh and only `doctor` and `pins` on the body can still flag it.

A permission or rule meant for one night or one batch gets `--expires` (`expires` in the MCP fields): a date, the last day it holds, an RFC3339 time, `3d` or `12h` from now, or `until:<id>`, until that item is done, shipped, rejected or archived. An expired note leaves the digest and the hooks and ranks last in search, marked `[expired]`. Closing the item it waits for, the SessionEnd background job and `breadcrumb doctor --fix --yes` unpin it and set a decision's `decision_status` to superseded, and `breadcrumb doctor` names what expired in the last two weeks.

## Duplicates and search

Search ranks a note the query names by id or slug first, then a note holding the whole query literally, then notes by how many of the typed words they hold literally, an identifier like import_loose_faces as a whole, then by matched terms and score. A literal hit says `(exact)` when the other hits are not, a partial match names its terms, `(2/3 terms: import, loose)`.

`add` names up to two existing notes that look like the same fact, by shared title words with shared tags helping, so an agent can update one of them instead. `search` lists notes matching more of the query first, then by score weighted by kind and recency, drops notes that only share a word or two with a long query, shows 5 by default and marks partial matches like `(2/3 terms)`.

## Who wrote what

`breadcrumb get <id>` hides what an import left (`source`, `metadata`, `source_hash`, `memory_name`), nothing leaves the file, `--full` and `--json` show it. It ends with what links to the note, `superseded by` first. `--tail N` keeps the last N lines of the text with a line saying how many were cut, History stays whole and does not count, since appends land above it. `--body` prints the text alone for piping, a cut line goes to stderr. The MCP `get` takes `full`, `body` and `tail`. `--json` always holds every key and the whole body, plus `inbound`.

Output names a note by `slug id`, or the bare id without a slug. The `KEY-id` form from older output, like `NEOCAD-yaxm9pf2`, still resolves as input everywhere, and `--json` and the web API keep their `key`. `breadcrumb update <id> --replace OLD NEW` changes one exact string in the body and refuses, changing nothing, unless it occurs exactly once. `update --body -` reads stdin, `--body-file` a file, and an empty one is refused rather than emptying the body. `breadcrumb move <id>... <state>` moves each on its own in one vault commit, a line per item, a failure leaves the others done and exits 1. `--position` takes one id. Search lines show the state of backlog items.

Every `add` stamps the session id in the `session` frontmatter key, every later `append`, `update`, `move`, `claim` or `release` stamps `last_session` when it was another session. Both come from `CLAUDE_CODE_SESSION_ID`, which Bash children, hooks and the MCP server all have. Old notes and notes old binaries write have no stamp and behave as before. An append starts with a line like `2026-10-31 neocad-4b a03e0d0a:`, a history line ends in `(by neocad-4b a03e0d0a)` or `(by lead a03e0d0a)` with `--by lead`, so never type dates or session ids by hand. The id stays because a name changes across a restart. `get` ends with `written by ...` in today's names, from `~/.claude/sessions`. `breadcrumb::session` has what other features need: `current()` for who this process is, `is_alive(id, 8 character prefix or name)`, `label(id)` for the name or the short id, `signature(id)` for both, `last_writer(note)`.

## Slugs

Every new note gets a short readable name beside its id, in the `slug` frontmatter key: two to four words from its title like `stress-auto-mesh`, filler words skipped, accented Latin letters plain, long words cut, always with a hyphen so it can never be read as an id, unique across the vault with a number on a clash. A title with no letter gives the kind and a number, like `task-123`. `add --slug` or the MCP `slug` argument sets a better one, a retitle never changes it, `update --slug` renames on purpose and old messages then stop resolving. Every command and MCP tool that takes an id takes a slug too, links store the id. Digest, board, search, list and move print `slug id` and always keep the id, since an old MCP server cannot resolve a slug. Notes without a slug work as before and show the id alone. `crumb add` keeps the id right after `added` for scripts. `breadcrumb slugs --backfill [--open-only] [--project p] [--yes]` names notes that lack one, dry unless `--yes`, open items first, without touching `updated`, and is safe to repeat. Maps, workflows and imported notes get theirs from the backfill. In messages to the user write the slug, with plain words beside it when it matters.

## Claims

Sessions that share a project claim what they work on: `breadcrumb claim <id>` (the `claim` tool) sets the item's `assignee` to the session name and records when, `breadcrumb release <id>` clears it. The name is `--by`, else `BREADCRUMB_SESSION`, else the start of the Claude Code session id. `next` skips items another session holds, the board and the digest show the holder under its current session name, and in-progress lines add the age since the last write or claim, or `(no owner)`. A claim with no write to its item for a day is stale: it shows as such and no longer keeps anyone away. Taking over or releasing someone else's fresh claim needs `--force`.

A claim also records where it was made, in `claim_machine` as `<machine> <assignee> <pid>`, from `breadcrumb::util::machine_name` and the session file at claim time, the two-word form without a pid still reads. A claim whose recorded process no longer runs (`procStart` tells a reused pid on Windows), with no live session under its assignee either, shows as stale at once, but keeps others away from `next` and needs `--force` on `claim` until an hour after its last write (`DEAD_GRACE`), since installing a binary means restarting sessions. A resumed session with the same id keeps its claim with no action. `being_built` follows the same rule. Leases free at once. `/clear` gives a running process a new session id: that session stays alive, and a caller whose own session file has the recorded pid is the holder, so its Bash children are neither refused nor stealing. An MCP server started before the `/clear` keeps the old id and gets a refusal naming the holder, which loses nothing. Session files only exist locally and the vault syncs, so when the machine differs, the key is missing (old binaries do not write it), the assignee is free text from `--by`, or there is no session list, only the one day rule applies. A session file that cannot be read or parsed could be anyone's, so while one exists nobody counts as dead.

Leads start lanes with workflows, so claim when a lane starts and record its ref: `breadcrumb claim <id> --by lead` and `breadcrumb update <id> --ref branch:x`. A `branch:` or `run:` ref on a queued item means work runs: `next` skips it for anyone but its holder, the digest lists it under `Being built` and the board in a `being-built` column, while the stored state stays queued, so nothing changes behind an agent's back and old binaries read the same file. A ref has no time of its own, so a claim that stopped holding ends this, a day without a write or an hour after a dead session's last write, and the item is handed out again. Moving an item back to the queue from in-progress, review or a closed state ends its old build: the refs move to the history, unless the same move adds them. `move` from queued straight to review warns that the item was never claimed.

## Questions

When a backlog item needs a decision from the user, ask through breadcrumb instead of guessing or waiting in chat: `breadcrumb ask <id> "Which palette?" -o "warm: reds and oranges" -o "cool: blues" [--multi] [--free]` (the `question` tool with action ask, two to four options with a short description each, `free` allows a text answer too). Questions sit in the item's `questions` frontmatter list, ids look like `<item>.<n>`. An open question locks its item: `next` skips it, `claim` refuses it with the reason, the board shows it in the `waiting-on-user` column and the digest names it, so pick other work. The user lists them with `breadcrumb questions` and answers with `breadcrumb answer` (walks them one by one on a terminal) or `breadcrumb answer <qid> 2`, `1,3` or `--text "..."`. When the user gives an answer in chat, record it with the `question` tool (action answer, `choices` or `answer` text). An answer unlocks the item and flags it unseen. Agents handle those first: `next` returns items with an unseen answer ahead of everything else, in any state, the digest has one line `answer arrived on <qid>: <question> -> <answer>` each, and `get` shows the answer. If the item is already built (review, done, shipped) adjust it to the answer, if not build it with the answer. Claiming the item (or `next --claim`) acknowledges the answer, `breadcrumb ack <id>` does it alone. `breadcrumb unask <qid>` withdraws a question that no longer matters. Items without questions behave as before.

## Review

Review means landed and waiting for the user's check, done means on the development build and accepted, shipped means in the beta. Say how to check it when moving an item to review: `breadcrumb move <id> review --step "Open the app" --step "Press Save, a toast shows"` (`steps` in the MCP `move`). Steps are ordinary acceptance criteria, and what the user sees is the criteria not yet marked `[x]`, so tick what you verified yourself. `--check` only ticks, `all` or positions like `2,3`, and refuses other text, so a step that reads `3` stays a step. `--step` is only for moving to review. Moving without any open step prints a warning, never a refusal, since old workflows and old binaries still do it. `breadcrumb review [--project p | --all]` (the MCP `backlog` view `review`) lists items in review, priority then oldest first, with their steps, or says they have none. The verdict is `breadcrumb review pass <id>`, to done with the steps marked met, or `breadcrumb review fail <id> --reason "..."`, back to queued keeping its priority, with the reason in the body, who said it in the history, the claim gone and the steps still open. Both refuse items that are not in review.

Promotion runs from refs, so record them when the work lands: `breadcrumb move <id> review --ref commit:<merge sha> --release-note "One line a maker reads"`. `release_note` is one line, also set by `breadcrumb update --release-note` and `release_note` in the MCP `move` and `update`. Moving to review without one prints a hint, and without a `commit:` ref or `shipped_in` a warning, neither refuses. `breadcrumb ship origin/main..dev [--repo DIR] [--project p] [--in NAME] [--yes]` reads `git log` of the range, in the checkout `map` would use, and never writes to that repo. An item matches when a `commit:` ref or any hex word of `shipped_in` is a prefix of at least 7 characters of a commit in the range. It prints the release note lines of matched items in review or done, those with no line, `Matched but not landed, not moved` with the reason for each, those already shipped or rejected, which it skips, and the merges no item points at. Every line names the state, a review item says how many steps are unchecked. Only `--yes` writes: matched items in review or done move to shipped in one vault commit, `shipped_in` set when `--in` is given, and unchecked steps do not stop them since the code ships anyway. Any other state stays, so a failed review back in queued, another session's in-progress item or an idea naming a commit never ship, nor does an item with an open question or an epic with open children. The dry run ends by naming done items with no `commit:` ref and no `shipped_in`, which no range can find, and leaves them alone. A range git cannot read is an error with a non-zero exit and nothing moved, an unknown ref on an item only never matches, a single ref without `..` is refused since it would read all of history.

## Machine facts

Machine facts, like where screen recordings, logs or build caches live on this PC or which tools are missing, go in notes of kind `env`: `breadcrumb add -k env -t "Screen recordings" --field location=C:/Users/me/Videos --field access=read-only`. Their `machine` field defaults to this computer (`BREADCRUMB_MACHINE` overrides the name), `breadcrumb env` lists this machine's facts as a table (`--all-machines` for every one), and the digest only says how many there are. A built-in kind that is newer than the vault is written into it the first time a note uses it.

## Leases

A lease holds something that is not an item on this machine, like a build dir, a worktree or the CI runner: `crumb lease <name> [--by who] [--ttl 4h] [--note text] [--path dir]`, `crumb lease --release <name>`, `crumb leases`. No MCP tool, agents use the CLI. One holder per name, names compare without case on Windows. Taking one another live holder has is refused and names the holder, `--force` takes over or releases, the same holder taking it again renews and keeps its note and path. A name that is an absolute path is also its path.

The holder is the session's 8 character id, or free text from `--by` or `BREADCRUMB_SESSION`. `--by` with a live session's name or id gives the lease to that session. A lease ends at its ttl, or at once when its holder is a session that had a session file when taking it and whose process has since gone, never while a session file is unreadable. The same process under a new id after `/clear` is still the holder. Free text only ends by ttl.

Leases live in `<vault>/.local/leases.json`, written whole under `.local/leases.lock`. `.local` is gitignored, so a lease never syncs, never commits and is no note, and old binaries do not read it. The `machine` field still guards a vault copied with its `.local`. The digest gets one `Leases on this machine:` line when any holds.

`crumb hooks install --bash-leases` adds a PreToolUse Bash hook, `crumb hook bash-lease`, plain `hooks install` neither adds it nor removes it. It refuses a command that names the path of a lease another session holds, equal or under it, in any slash style or as /d/dir, and a command that contains `cargo` or runs a script (.sh, .ps1, .py, .bat, .cmd) while `CARGO_TARGET_DIR` in the hook's environment is that path. `git status` and the like are not touched by that variable. The reason names the holder and both ways past: `BREADCRUMB_LEASE_OK=1` anywhere in the command lets that one through, `crumb lease <name> --force` takes it over. Parts of a command that call crumb or `git commit` do not count, their text is prose and the way out has to stay open. It reads one small file, sessions only on a match, and any failure passes. It reads the command text only, so a path set inside a sourced script or reached by a relative path gets through, and so does the session's cwd.

## Code maps

Code maps save what an agent learned about one area of a project, so the next one does not grep for it again: `breadcrumb map put "stress overlay" --line "src/view/overlay.ts:42 setStressOverlay, turns the overlay on"` (repeatable, or `--lines-file`, the `map` tool with action put). One map per area and project, a put merges by file and symbol, replacing the old line, and records the git blob hash of each named file in the checkout (the one holding the cwd, a recorded project path or `--repo`). `breadcrumb map get <area>` marks lines whose file changed or vanished since as `[stale]` and names them in its header line. `breadcrumb brief <files, dirs or areas>` (the `map` tool's default action) returns the matching map lines and the gotchas, decisions and feedback whose `paths` globs match, ranked and cut to about 2k tokens with a line saying what was cut.

## Staleness

Notes carry a `verified` date, set on every write. `breadcrumb verify <id>` confirms a note is still accurate without changing it, notes older than `stale_days` (breadcrumb.toml, default 60) get a `(stale?)` marker, and `breadcrumb doctor` lists them along with backticked repo paths that no longer exist in the project checkout. `breadcrumb stats --prompt "..." --file src/x.rs` shows what the hooks would inject.

## Upgrade and serve

`breadcrumb upgrade` rebuilds from the source checkout and reinstalls even while an MCP server or `breadcrumb serve` holds the exe open on Windows, running processes keep the old version until their client restarts them. Killing `breadcrumb serve` between requests is safe, writes happen under the vault lock and Ctrl+C lets in-flight requests finish.

## Answering from the web

`breadcrumb serve` (127.0.0.1:7878) has a Questions page at `/questions`, linked from the start page: open questions across projects with their item and project, each option as a button with its description, several picks when the question is multi, free text when it allows it, and a second list of answers no agent has acknowledged yet. It uses `GET /api/questions` and `POST /api/question/<qid>/answer` with `{"choices": [1, 3], "text": "..."}`, which run the same checks as `breadcrumb answer`.

The Review page at `/review` sits beside it: each item in review with what to try, Pass, and Fail, which asks for a reason. It uses `GET /api/review`, `POST /api/review/<id>/pass` and `POST /api/review/<id>/fail` with `{"reason": "..."}`, which do the same as `breadcrumb review pass` and `fail`, and record `web` as who.

For the phone, run `breadcrumb serve --remote --allow-host <name>` (repeatable) behind a TLS proxy such as `tailscale serve --bg 7878`. It still binds 127.0.0.1 only. It accepts those Host names as well, writes `serve-token` (256 bit, owner only where the OS allows) under the user's app data directory, outside the vault, and prints `https://<name>/login?token=...`. Opening that link once per device stores the token in an HttpOnly, Secure, SameSite=Strict cookie, delete the file and restart to rotate it. Every request needs the cookie, otherwise it gets a login hint page and no data. Remote mode allows only the Questions and Review pages, their list, answer and verdict endpoints, and a read only board at `/board`, everything else answers 403. Without `--remote` nothing changes.
